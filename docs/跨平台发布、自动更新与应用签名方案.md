# CyberArm 跨平台发布、自动更新与应用签名方案

版本：1.0｜日期：2026-09-14｜适用分支：features/simulator

## 1. 目标

CyberArm 最终以 Windows、macOS、Linux 桌面应用交付。用户安装一次后，后续通过版本检查、下载和重启完成更新，不需要重新配置项目、动作、场景或标定数据。

首选技术路线：Electron + React/Three.js + FastAPI sidecar + C++ 动态库 + electron-builder + electron-updater。

## 2. 应用结构

```text
CyberArm 桌面应用
├─ Electron 主进程：窗口、更新、生命周期、文件和子进程
├─ React/Three.js：三维工作台和控制界面
├─ FastAPI sidecar：IK、规划、动作、WebSocket 状态
├─ C++ core：FK、夹爪闭链、轨迹和碰撞计算
└─ 资源：robot.glb、robot.json、collision.npz
```

Electron 主进程启动 FastAPI 子进程，等待本机健康检查成功后再加载前端。服务使用随机回环端口，并通过环境变量传递端口、资源目录和用户工作区目录。窗口关闭时先停止规划任务和模拟服务，再退出 Electron。

## 3. 三个平台的产物

| 平台 | 推荐产物 | C++ 核心 |
|---|---|---|
| Windows x64 | NSIS 安装包、便携 ZIP | `.dll` |
| macOS arm64/x64 | DMG，或 Universal 包 | `.dylib` |
| Linux x64 | AppImage；可选 deb/rpm | `.so` |

C++ 使用同一套 CMake 工程在各平台分别编译，保持 C ABI 和参数格式一致。Python sidecar 也必须按目标平台单独构建，不能把 Windows 的 exe 放进 macOS 或 Linux 包。

## 4. 自动更新流程

```text
CI 构建三个平台
  ↓
发布版本和更新元数据
  ↓
客户端检查版本
  ↓
后台下载
  ↓
空闲状态下提示重启
  ↓
备份工作区并安装
```

使用 `electron-updater`。发布服务器可以先使用 GitHub Releases，后续迁移到 Cloudflare R2、S3 或自建 HTTPS 文件服务器。每个版本必须上传对应平台的安装包和元数据文件。

默认策略：启动时检查一次，运行期间定时检查；发现新版本后不强制关闭；下载完成后等待用户点击“重启并更新”。模拟运行、规划任务、真实机械臂运动期间禁止安装，只允许下载。真实设备已停止且状态保存成功后才允许安装。

更新前备份：

```text
用户动作文件
场景和障碍物
用户设置
舵机映射和零位
未来的视觉标定数据
```

程序文件可以替换，用户数据不能放在安装目录。建议使用平台用户数据目录：

```text
Windows: %APPDATA%\CyberArm
macOS:   ~/Library/Application Support/CyberArm
Linux:   ~/.config/CyberArm
```

更新失败时保留旧版本和用户数据。版本号使用语义化版本：`0.1.1` 修复问题，`0.2.0` 增加功能，`1.0.0` 表示稳定版。稳定、Beta、Alpha 使用不同更新通道。

## 5. Windows 签名

### 5.1 个人开发者的选择

Windows 对公开分发的 EXE/MSI 推荐使用受信任的代码签名方案。微软当前推荐非商店分发使用 Azure Artifact Signing（原 Trusted Signing）；个人开发者目前的可用区域限制为美国和加拿大，基础档约 9.99 美元/月，另需付费 Azure 订阅并完成身份验证。它不保证新文件立即消除 SmartScreen 提示，发布者身份需要通过连续版本积累信誉。

如果无法使用 Azure Artifact Signing，可以购买 CA 的 OV 代码签名证书，官方资料给出的常见范围约为 150–300 美元/年；不同 CA、存储方式和套餐可能更高。OV 私钥通常要求放在硬件令牌或云 HSM，需把签名工具接入 CI。

EV 证书目前不值得只为绕过 SmartScreen 购买。微软说明自 2024 年起，EV 文件也要经过信誉积累，不能再把高价 EV 当作首次下载零警告的保证。

### 5.2 最低成本方案

开发和内部测试可使用自签名证书，费用为零，但普通用户的 Windows 不会默认信任它，只适合测试机或企业统一部署证书的环境。

如果通过 Microsoft Store 发布 MSIX，商店认证后会重新签名，签名本身免费；但 MSI/EXE 路径仍需要发行者负责签名。商店适合后续正式发布，不一定适合作为当前开源项目的第一分发渠道。

### 5.3 Electron 配置方向

使用 `electron-builder` 的 Windows NSIS 目标，CI 中使用 `signtool` 或 Azure Artifact Signing 对安装包及内部 PE/DLL 签名。签名身份要长期保持一致，不能每个版本更换证书，否则信誉积累会中断。

## 6. macOS 签名和公证

### 6.1 个人开发者成本

在 Mac App Store 外分发 DMG 或 `.app`，需要 Apple Developer Program 的 Developer ID 证书和 notarization。个人账号可以注册，Apple Developer Program 当前费用为 99 美元/年。该会员资格包含 Developer ID 和 Mac 应用公证所需能力；公证服务本身没有按应用或按次数单独收费。价格以 Apple 账号所在地区结算金额为准。

没有付费会员时，可以用 Apple Account 做本机开发和测试，但不能把它当作面向公众分发的 Developer ID 签名方案。

### 6.2 签名流程

```text
构建 .app
  ↓
codesign --deep --force --options runtime
  ↓
生成 DMG
  ↓
对 DMG 或 .app 做 Developer ID Application 签名
  ↓
xcrun notarytool submit
  ↓
xcrun stapler staple
  ↓
验证 Gatekeeper
```

Electron 应用通常需要启用 hardened runtime。签名和公证密钥不写入仓库，放在 CI 的加密密钥或 Apple 公证凭据中。Apple Silicon 和 Intel 应分别构建，或者在 Mac 上合并为 Universal 应用。

跨平台成本中容易遗漏的是构建环境：macOS 签名、公证和最终验证必须在 Mac 或可信的 macOS CI runner 上完成，单独购买 Apple Developer Program 并不能替代 Mac 构建环境。

## 7. Linux 签名和发布

Linux 没有统一的桌面签名体系。首版推荐 AppImage，并通过 HTTPS、GitHub Releases 或对象存储发布；同时提供 SHA-256 校验值。需要发行版集成时再补充 deb/rpm，并由对应仓库或包签名体系管理。

Linux 自动更新可以由 `electron-updater` 处理 AppImage，也可以在后期改成提示用户下载新 AppImage。不要把 Linux 的更新逻辑强行套用 Windows 的证书模型。

## 8. 建议预算

个人开发者、不开通商店销售时，最低可按以下方式估算：

| 项目 | 预算 |
|---|---:|
| Windows 自签名测试 | 0 美元 |
| Windows Azure Artifact Signing（若地区和身份符合） | 约 9.99 美元/月 + Azure 订阅 |
| Windows OV 证书备选 | 约 150–300 美元/年起 |
| macOS Developer ID 与公证 | 99 美元/年 |
| Linux AppImage 发布 | 通常 0 美元 |
| GitHub Releases | 可使用仓库已有发布能力 |
| macOS 构建机或 CI | 视本地设备/CI 服务另计 |

因此，最现实的个人开发者起步方案是：Windows 先用自签名做内部测试，macOS 购买 99 美元/年 Apple Developer Program，Linux 发布 AppImage；准备向公众提供 Windows 安装包时，再根据所在地区选择 Azure Artifact Signing 或 OV 证书。

## 9. CyberArm 的安全更新规则

1. 不在机械臂运行或模拟执行中安装更新。
2. 安装前自动停止规划任务并保存工作区。
3. 更新包验证签名、版本和目标平台后才执行。
4. 程序版本、模型版本、C++ 核心版本一起记录。
5. 模型或运动学版本变化时，旧动作只允许导入和重新预览，不允许直接执行。
6. 更新失败时显示明确错误，保留上一版本和用户数据。
7. 稳定版、Beta 版和开发版使用不同通道。
8. 任何签名私钥、Apple 凭据和 Azure 凭据只放在本地安全存储或 CI Secret 中。

## 10. 费用与地区核对（2026-09-14）

Apple 官方当前列出的 Apple Developer Program 费用为 99 美元/会员年。Windows 官方当前列出的 Azure Artifact Signing 基础计划为约 9.99 美元/月、最多 5,000 次签名；个人开发者的公共信任资格目前限美国和加拿大。如果开发者所在地不符合该条件，应考虑 CA 的 OV 代码签名证书，微软文档列出的常见费用约 150–300 美元/年。

微软当前文档明确说明，EV 证书不再自动带来即时 SmartScreen 声誉；Azure Artifact Signing 和 OV 都需要通过连续发布积累发布者信誉。因此不应为了“首次下载零警告”单独购买高价 EV。

如果个人开发者账号在中国大陆或其他不在微软个人资格范围的地区，默认按 OV 证书预算规划；也可以先发布未签名测试包，或研究 Microsoft Store 的 MSIX 分发。实际资格和税费以账号地区、身份验证结果及服务页面为准。

## 12. 无额外账户的手动更新方案

如果暂时不购买代码签名证书、不注册 Apple Developer Program，也可以只使用现有 GitHub 仓库和 Releases 发布程序。这里的“手动”只表示用户主动点击“检查更新”；发现新版本后，客户端可以自动下载更新包、退出旧程序、启动安装器覆盖旧版本并重新打开新版本。该方案不需要 Azure、S3、Cloudflare、Apple Developer 或其他更新服务账户。

推荐流程：

```text
GitHub Actions 构建三个平台
  ↓
上传 GitHub Release 资产和 SHA-256 文件
  ↓
客户端读取公开版本信息
  ↓
显示版本、变更说明和下载按钮
  ↓
用户点击“更新”
  ↓
客户端自动下载、退出、安装并重启
```

客户端可以请求一个项目内的 `update-manifest.json`，也可以查询 GitHub Releases 的公开 API。检查动作由用户触发，安装动作由更新器自动完成。清单建议包含：

```json
{
  "version": "0.2.0",
  "notes": "修复路径预览和模型加载问题",
  "assets": {
    "win-x64": {"url": "...", "sha256": "..."},
    "mac-arm64": {"url": "...", "sha256": "..."},
    "mac-x64": {"url": "...", "sha256": "..."},
    "linux-x64": {"url": "...", "sha256": "..."}
  }
}
```

下载后，CyberArm 应校验 SHA-256，并检查文件是否对应当前平台和架构。校验通过后显示“打开下载目录”或“运行安装程序”，不在机械臂运动、模拟运行或规划任务期间覆盖程序文件。用户数据和标定数据仍保存在用户目录，不随安装包替换。

### 12.1 “手动检查、自动安装”的行为定义

用户点击“检查更新”后，应用执行以下状态机：

```text
检查版本 → 询问是否更新 → 下载 → 校验 SHA-256 → 保存工作区
→ 等待机械臂停止 → 退出旧程序 → 安装/覆盖 → 自动启动新程序
```

Electron 主进程负责更新，不让 React 页面直接替换自身。Windows 使用 NSIS 安装器和 `quitAndInstall()`；macOS 在签名公证后使用 Electron 更新器，未签名版本保留辅助安装和用户确认回退；Linux AppImage 可以替换新文件后重新启动，或提示用户确认执行权限。更新失败时启动旧版本并保留用户数据。

### 12.1 各平台限制

- Windows 未签名安装包可能出现 SmartScreen 警告，用户首次运行时需要允许；确认信任后，NSIS 更新器可以自动下载、退出、覆盖和重新启动。
- macOS 未使用 Developer ID 签名和公证时，Gatekeeper 可能阻止首次打开；同时，Electron 原生自动更新通常要求签名应用。未签名版本可以下载更新并启动辅助安装流程，但无法保证在所有 macOS 安全状态下完全无人确认地覆盖和重启。
- Linux AppImage 通常不要求申请签名账户，但用户需要给文件执行权限；发布 SHA-256 校验值可以防止下载损坏。

### 12.2 第一版推荐

个人开发初期可以采用：

```text
GitHub Releases
+ GitHub Actions 构建
+ update-manifest.json
+ SHA-256 校验
+ Electron 内置“检查更新”
+ 用户确认后手动下载和安装
```

这是一种低成本、低耦合的发布方式。后续购买签名证书或需要更稳定的后台更新时，再切换到 `electron-updater` 的自动下载和重启安装；版本清单、Release 资产和用户数据目录可以继续复用。

## 11. 当前决策

当前采用 Electron，不重写 React/Three.js 和 FastAPI。下一步增加 Electron 主进程、sidecar 管理、随机端口、跨平台资源路径和 electron-builder 配置；然后为 Windows、macOS、Linux 建立独立构建任务。视觉模块和真实舵机通信继续复用同一桌面外壳，不改变自动更新和签名边界。
