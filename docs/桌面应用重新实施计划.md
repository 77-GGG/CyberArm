## 2. 重新设计的核心判断

桌面交付包含进程管理、资源分发、数据持久化和版本升级。安装包生成与 /api/state 返回正常只是局部验证，不能代替安装后完整验收。

统一跨平台结构，使用 desktop/ 管理共用 Electron 代码及构建入口；不再把通用主进程写在 windows 目录中。当前平台配置集中在 desktop/package.json，后续复杂平台资源再拆出独立构建目录。

| 组件 | 职责与边界 |
| --- | --- |
| Electron 主进程 | 窗口、后端启动与退出、用户目录、文件对话框、日志、更新协调 |
| preload | 暴露经过参数和调用来源验证的有限接口；不暴露通用 Node 或任意 IPC |
| React/Three.js | 复用模拟工作台；增加启动失败、版本信息、更新状态等桌面交互 |
| FastAPI 子进程 | 继续承载 IK、规划和状态；提供就绪信息、任务停止和退出接口 |
| C++ 核心 | 按平台构建 DLL/dylib/so，以一致接口供 Python 调用 |

建议首轮沿用本机服务提供前端和 API 的同源结构，避免同时更换现有通信方式。服务仅监听回环地址，使用启动会话凭据并验证请求来源，避免其他本机网页控制服务。端口由后端绑定系统分配端口，再通过结构化就绪消息通知主进程，避免先查空闲端口再启动的竞争。

Electron 启用上下文隔离、渲染进程沙箱，关闭 Node 集成；限制导航、弹窗和外部链接。只加载随应用分发的工作台代码。依据：[Electron 安全指南](https://www.electronjs.org/docs/latest/tutorial/security)。

## 3. 生命周期与数据

启动顺序：单实例检查 → 创建用户目录和日志 → 启动后端 → 校验就绪消息、版本、模型和核心加载 → 显示工作台。失败必须有明确错误、日志位置和重试入口，不能停在空白窗口。

正常退出和升级退出共用关闭流程：阻止新任务 → 停止规划/执行 → 保存数据 → 后端确认退出 → 确认子进程树结束 → 关闭应用。超时必须报告并处理；不能用“后端还活着”判断机械臂忙碌，后端在空闲时也应正常运行。

资源目录只读；作业、设置、场景、日志写入用户数据目录。项目保存使用原子写入。记录应用、模型、核心和数据格式版本，升级前备份并验证迁移。模型改变后要求旧动作重新预览。

## 4. 构建策略

首轮建议将 Python 后端以目录形式完整打包，并由安装器封装全部文件。相比单文件解压方式，更容易检查运行库、资源路径和进程退出；外部用户仍获得一个安装程序。此项为新方案建议，不代表已实现。

构建任务顺序：锁定依赖 → 编译目标平台 C++ 核心 → 构建前端 → 打包 Python 及全部运行库 → 检查资源清单与版本 → 后端冒烟测试 → Electron 解包运行验证 → 安装包 → 干净系统安装验收。

任一命令失败立即停止，禁止复用旧产物报告成功。构建不临时修改项目依赖版本。Windows、macOS、Linux 分别构建和测试；macOS arm64/x64 首轮分包，暂不增加 Universal 合并复杂度。

## 5. 更新方案统一

保留用户确定的交互：主动检查更新 → 显示版本说明 → 点击更新 → 下载并校验 → 保存工作区并等待任务安全停止 → 退出旧应用 → 覆盖安装 → 自动打开新应用。下载期间可以继续使用，安装前需重新检查状态；不自动开始定时检查或强制更新。

使用 GitHub Releases 分发。拟选 electron-builder + electron-updater，直接使用其平台元数据和更新协议；首轮不再并行维护自定义 update-manifest.json 更新器。SHA-256 可供人工校验，但不能替代可信发布来源或代码签名，也不能仅凭校验和承诺防篡改。

| 平台 | 交付与更新承诺 |
| --- | --- |
| Windows | 以 NSIS 安装版为主，验证用户点击后自动安装及重启；未签名包接受系统提示，不能承诺无提示 |
| macOS | DMG 用于首次分发；自动更新所需资产按选定更新器生成并验证。未签名阶段提供下载及明确安装引导，不承诺无人确认覆盖重启 |
| Linux | 首轮 AppImage；验证其可写位置、权限与更新器适配，deb/rpm 暂不纳入应用内覆盖更新 |

Electron 原生 autoUpdater 在 macOS 要求签名，Linux 不受其内置支持；不要将其与 electron-updater 的能力混为一谈。依据：[Electron autoUpdater 平台说明](https://www.electronjs.org/docs/latest/api/auto-updater)。无需额外服务账户的分发目标可以保留，但不能据此承诺所有平台具有相同的无签名自动安装体验。

下载或校验失败应保留当前运行版本；安装开始后的故障恢复依赖平台安装器，不能未经验证就承诺自动回滚。提供数据备份和旧版本恢复说明，使用实际版本升级演练验证恢复路径。

## 6. 实施顺序和验收门槛

1. **设计评审**：确认组件边界、目录、启动退出协议、更新平台差异。本阶段交付文档，等待用户过目。
2. **运行基础**：实现共用 Electron 外壳及用户目录、后端生命周期。验收重复启动、启动失败提示、正常关闭、异常退出清理和重新打开。
3. **功能集成**：在桌面窗口验收模型、关节控制、预览、执行、停止、保存与重新打开；核对数据真正落盘。
4. **Windows 交付**：在无 Python、Node 和开发工具的干净 Windows 环境安装运行；覆盖中文路径、空格路径、普通用户权限、卸载及用户数据保留策略。
5. **更新闭环**：使用两个真实版本验证升级和自动重启、数据迁移、下载失败、校验失败、忙碌状态阻止安装及故障恢复。完成后才宣称支持应用内更新。
6. **跨平台验收**：分别完成 macOS 和 Linux 的安装运行、资源加载、退出和对应更新测试；缺少设备时明确标为未验证。

每阶段记录复现步骤、修复内容和验证证据。未完成前置门槛，不以提前生成安装包替代验收。本轮不实现视觉模块或真实舵机通信。
