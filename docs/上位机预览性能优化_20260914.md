# CyberArm 上位机预览性能优化与碰撞检查口径

更新：2026-09-14｜分支：release/windows-packaging｜改动文件：simulator/backend/cyberarm/planner.py

本轮不动前端界面、不动模型几何、不动 C++ 核心（沿用已编译的 libcyberarm_core.dll），只改规划内核的计算口径。用户反馈两条：关节控制（点动）预览等待过长；末端（笛卡尔）目标求解过慢。下面记录根因、实测数据、改动和仍然存在的边界。

## 1 结论摘要

| 用户反馈 | 根因 | 验收数字 |
|---|---|---|
| 关节预览等太久 | 路径检查把整段的位移保守界一次性压在同一个节点上，夹爪方向的 pad 被抬到几十毫米，窄相碰撞查询按 ceiling 计费，于是每次查询都变贵 | 关节 8° 预览 2583 ms → 102 ms；关节 30° 预览 3.599 s → 0.178 s；夹爪 20° 预览 1.520 s → 0.137 s |
| 末端目标算得慢 | IK 的解析雅可比取了错误的旋转轴（x 轴而不是 z 轴），高斯-牛顿方向基本无效，只能靠信任域和有限差分慢慢收敛；同时每轮迭代在 Python 层循环做 FK 和叉乘 | 近点目标 79 ms → 1 ms；上移 30 mm 8 ms → 不足 1 ms；下移 25 mm 15 ms → 1 ms；不可解目标 308 ms → 157 ms |

两处改动都没有放松判据：碰撞的接受条件仍是「整段每个姿态间隙 > 0.2 mm」，IK 的接受条件仍是「位置误差 ≤ 0.0005 mm 且方向误差 ≤ 0.5°」。第 8 节给出重新验证的记录；第 9 节列出仍然慢的场景和原因。

## 2 测量方法

同一脚本 .cache/prof_perf.py 改动前后各跑一次：改动前结果存 .cache/perf_before.json，改动后存 .cache/perf_after.txt。逐关节预览用 .cache/prof_joints.py（取第二轮预热值，第一轮含首次构建 Geometry 的开销）。窗口内是单次运行值，用于判断数量级差异，不是统计量；本机为 Windows + Python 3.12（simulator/.venv），C++ 核心未重编。

## 3 根因一：解析雅可比取错关节轴

core.cpp 的 ca_fk 让每个关节链 frame 绕自身局部 z 轴旋转，正确的轴向量是 frames[k][:3,2]。旧实现写成了 frames[k][:3,0]（x 轴），所以解析雅可比与真实运动方向不符。

证据（.cache/debug_jac.py，把解析雅可比与有限差分逐项比较）：

| 版本 | 最大绝对误差（两例） |
|---|---|
| 旧（x 轴） | 0.3324 / 1.3870 |
| 新（z 轴） | 1.49e-9 / 1.29e-8 |

雅可比错的时候 least_squares 仍会退化成内部差分，所以不是「算错」，而是每一步都在做无用功，收敛慢、迭代次数多。这是末端目标慢的第一来源。

## 4 根因二：每轮迭代的 Python 层循环

两处改动：

1. 一次 FK 同时取 5 个轴的轴向量和原点，用 np.multiply(np.cross(axes, p - origins).T, POSITION_GAIN, out=jacobian[0:3]) 直接写进预分配数组；方向约束行同理。旧写法每个轴一次 numpy 调用，时间花在派发而不是算术上。
2. least_squares 的 fun 和 jac 是两次回调，旧实现等于每步算两遍残差函数。现在残差函数把最后一次求值（x 和雅可比）留给 jac 复用。
3. 新增 tcp_frames(robot, points)：直线检查要对一条线段取 200 个采样点，逐点调用 robot.fk 是 200 次库调用，现在一次向量化算完（与逐点结果的最大差 4.44e-16）。straight_waypoints 的偏差检查改用它。

## 5 根因三：缺少热启动通道

新增 polish(seed)：阻尼高斯-牛顿加回溯，常量 POLISH_TOLERANCE = 1e-3（毫米量级的残差就够）、POLISH_ITERATIONS = 40、POLISH_BACKTRACK = 8。

- 命中（位置误差 ≤ 0.0005 mm 且方向误差 ≤ 0.5°）直接返回，不走 least_squares。
- 未命中时把 polished 的结果插到零位种子之前，作为比两个端点更好的冷启动种子。
- 可复现性：种子列表先按「当前姿态、零位、固定随机种子 20260914 的采样」确定好，再调用 polish；polish 失败或没命中都不改变冷启动序列，因此同一输入的求解路径可重复。

点动预览和末端微调的目标都离当前姿态很近，正是热启动起作用的场景：近点 10 mm 目标 79 ms → 1 ms。

## 6 根因四：扫掠 pad 过大（关节预览慢的主因）

### 6.1 机理

check_segment 把一个运动段切成节点，对节点中点和节点区间做一次保守碰撞查询：先用「区间内两个物体各自可能移动的距离」把间隙减掉，只有减完还剩 0.2 mm 以上才认为这一段整体安全，否则细分或改测精确间隙。

这个「可能移动的距离」就是 pad。窄相碰撞查询 ca_mesh_gap 的代价由 ceiling 决定：它以 ceiling 起步、只在降到 0.2 mm 以下时提前返回，所以 ceiling 越大越慢。实测曲线（.cache/now_ceil.txt，一对齿轮/连杆，真实间隙 1.620 mm）：

| ceiling | 返回 | 耗时 |
|---|---|---|
| 0.201 mm | 0.201 mm | 0.760 ms |
| 0.5 mm | 0.5 mm | 1.627 ms |
| 1.0 mm | 1.0 mm | 3.578 ms |
| 2.0 mm | 2.0 mm | 12.958 ms |
| 4.0 mm | 1.620 mm | 14.511 ms |
| 10.0 mm | 1.620 mm | 20.280 ms |

旧实现对所有关节统一用 0.7 m/rad 的位移界，夹爪也一样。夹爪闭链的实际速度远小于这个值：夹爪本体到夹爪轴的距离只有几厘米，实测每弧度最大位移 0.0465 m。用 0.7 估算等于把 pad 放大 15 倍，一段 8°（0.14 rad）的夹爪运动就会得到约 49 mm 的 ceiling，于是：

- 每次窄相查询都要把 BVH 从 49 mm 一路降下来，单次查询几十毫秒；
- pad 比真实间隙（齿轮与连杆只有 1.6 mm）大一个量级，padded 间隙一直为负，于是节点被反复细分到远小于必要尺寸才敢接受。

证据：.cache/prof_grip3.py 显示夹爪 8° 预览合计 2419 ms，其中窄相碰撞 2339 ms、3140 次调用；同幅度其它关节 46–60 ms。

### 6.2 决策：夹爪扫掠半径按实测取值

新增 gripper_sweep_radii()（.cache 中的探针 .cache/verify_grip.py 可复现）：

- 在夹爪关节的整个行程上取 129 个采样点，只用夹爪角驱动一次 FK；
- 对每个 frame >= 6 的网格，取包围盒的 8 个角点，算相邻采样点之间的最大位移，除以角度步长，再乘 1.25 的裕量；
- 结果按网格索引缓存在 lru_cache(maxsize=1) 里，一次性测量耗时 7.95 ms。

实测半径：最大 0.046458 m/rad（ARD_09_Link_Left），其余夹爪网格 0.0386–0.0463；frame 11 组（gear2 / Link_Right 一路）因为和对心关系不同，9 个网格取值 0.0060–0.0463。

扫描 129 个点足以覆盖整段行程的理由写在函数注释里：夹爪的颚、连杆和齿轮是一条闭链，只由夹爪角驱动，所以每个夹爪刚体相对手掌的姿态是这单一角度的函数，扫完行程就覆盖了全部可达姿态；速度随角度平滑变化，相邻采样点之间的最大割线就是扫描间隔内的最大速度，裕量覆盖间隔内的余量。

### 6.3 为什么一次扫描对所有基座姿态都成立

夹爪关节只影响 frame >= 6 的物体（influence[:,5] = frames >= 6），基座关节只是整体旋转夹爪，不改变夹爪内部的相对速度。验证（.cache/verify_grip.py 输出 .cache/verify_grip.txt）：取 5 个随机基座姿态，实测「最大位移率 / 表中值」全部等于 0.8000，正好等于 1 / 1.25（裕量），说明测得的速度与表值一致、裕量没有被吃掉，也就没有低估计。

### 6.4 仍然使用通用估计的地方

5 个串行关节仍用 SWEEP_PER_RADIAN = 0.7 m/rad：

- check_segment 的 pad（相对运动界）与地面、障碍物的 pad 都用它；
- straight_waypoints 的二阶导界也用它。

原因是这两处需要「任意姿态下都成立」的上界，而不是某个关节的实际速度，而且对小于 0.5 m 的臂来说 0.7 m/rad 仍然留有裕量。夹爪只在这两处也被单独替换成实测值。

### 6.5 分段策略（PAD_TARGET）

即使 pad 变小，如果整段只用一个节点，节点越大 pad 仍然越大。现在 check_segment 先按「总关节行程 × 0.7 / PAD_TARGET」把段切成若干小块，再对每块做同样的检查：块小，pad 就小，窄相查询便宜，而且大部分块在粗过滤阶段就被判定安全，不必进入窄相。

同一改动让检查节点数上升（例如 j1 转 30° 从 31 个节点变成 92 个），但因为每个节点都变便宜了，总时间反而下降一个量级（3.575 s → 0.168 s），而且节点数上升本身意味着检查更密。

PAD_TARGET 是否要放大到 0.008/0.01：实测比较过（.cache/pad_verdict.py，43 个场景 × 5 个取值），判决结果完全一致（verdict mismatches 为空），总耗时 0.004/0.006/0.008/0.010/0.012 分别是 10105 / 9748 / 10557 / 10723 / 12196 ms，没有系统性收益，放大后 j3、j4、j5 反而更慢（节点少了但每个节点的 pad 大了），因此维持 0.004。

## 8 正确性验证

### 8.1 单元测试

python -m pytest simulator/tests -q 通过（6 项），与本轮改动前一致。

### 8.2 接受必须等于安全（.cache/audit_accept.py）

check_segment 只用少数几次带 pad 的查询来给整段背书，所以真正有效的检验是：凡是被接受的段，用密集采样重新测精确间隙，看有没有一个姿态其实不满足。

70 个场景（6 个关节 × ±8/±20/2/5/8/12/30°、30 个随机段、2 个障碍场景），每个被接受的段用 129 个采样点复测：

- accepted-but-not-clear: 空（零漏检）；
- 被接受段的最密采样最小间隙都是 0.2010 mm，等于硬上限，说明这些段离碰撞很远；
- 最慢的三个：j4 转 30° 207 ms / 92 节点、j3 转 30° 214 ms、随机段 rand24 215 ms。

同一组场景也对旧实现（HEAD 版 planner 的副本）跑了一遍：旧实现的 accepted-but-not-clear 同样为空。也就是说本轮改动改的是速度与报告数值的口径，两版在「哪些段被接受」这件事上同样没放水；差别在于旧实现要花更长的时间、并且报出的最小间隙被 pad 压低（见 8.3）。

### 8.3 与旧实现的差异审计（.cache/verify_equiv.py）

43 个姿态逐例比较 clearance，7 例数值不同，其中 5 例是新实现「更不保守」，全部出现在夹爪关节方向：

| 场景 | 旧（mm） | 新（mm） | 差（mm） |
|---|---|---|---|
| 夹爪 15° | −181.64 | −22.67 | +158.97 |
| 夹爪 7.5° | −90.01 | −10.53 | +79.48 |
| 夹爪 2.0° | −22.81 | −1.62 | +21.20 |
| 夹爪 0.5° | −4.49 | +0.0002 | +4.69 |
| 随机段 5 | −213.61 | −27.02 | +186.59 |

这 5 例不是回归，而是旧口径的假象。可以精确验证：夹爪 0.5° 那一例，齿轮与连杆的真实间隙是 1.620 mm（第 6.1 节曲线里同一对物体的精确值），旧 pad 是 0.7 × 0.5° = 6.109 mm，报出来的数 = 1.620 − 6.109 = −4.489 mm，正好等于旧值。也就是说旧实现报的「几十毫米穿透」其实是「pad 减去的量」，不是几何距离；新实现给出的是真实几何距离（−1.62 mm 到 −27.02 mm，即真实穿透 1.6–27 mm）。

判决没有被翻转：这些场景在两版里一个仍然是「拒绝」（真实穿透），另一个是旧的 padded 值先触发细分、随后用精确间隙判定，最终结论与新版一致（第 8.2 节的密集复测是最终判据）。障碍物几何的三例（低、高、中点）两版数值完全相同；check_segment 的接受/拒绝对照（j1 ±30°、j2 +25°、j5 +20°、j1 +12°、j3 +8°、带障碍两例）方向完全一致。

另外两例差异是旧实现漏检：关节 2 转 15°/7.5° 时旧版只看到 ARD_04_Arm_01 / ARD_06_Arm_03 的间隙，新版还看到更近的 REVC_S04_HORN_DRILL_2p2（−15.30 mm 的差）。新版报出更近的一对，属于收紧而不是放松。

### 8.4 已知语义变化

唯一的语义变化是「被报告的最小间隙」在夹爪方向变小（旧值被 pad 抬高）。界面上显示的间隙数字因此更接近真实几何，数值会比以前小；判定文本与拒绝理由不变，前端文案与交互本轮未改。

## 9 已知残留

1. 单次大 pad 的 clearance 仍慢。probe 里对单个 15° 区间直接调用 clearance（不分段）时，关节 0 方向约 341 ms（改动前 350 ms），关节 1 方向 337 ms → 867 ms。原因是这时 pad 本身就是几十毫米，ceiling 由 best + pad 决定，排在最前面的候选对必然要付一次大 ceiling 的查询。实际路径检查不走这条路径：check_segment 先分段，每段的 pad 都在 4 mm 量级（见 .cache/perf_after.txt 里各段 0.1–0.2 s）；应用里唯一直接调用 clearance 的地方是开跑前的初始场景检查，传入的 delta 为空。
2. 不可解目标的 IK 略慢（42 → 73 ms、46 → 90 ms）。这两个场景本来就没有解，热启动最多迭代 40 步才放弃；量级仍在 0.1 s 以内，属于可接受范围。若以后要压，可以在热启动连续两次没有下降时提前退出。
3. clearance 的候选排序改成「padded 下界从小到大」。它让 best 掉得更快，但个别场景会先查一个 pad 很大的对（见第 1 点）。如果将来要优化，方向是按已更新的 best 复用查询结果，而不是再动 PAD_TARGET。
4. C++ 核心未重编，macOS/Linux 需要各自的 .so/.dylib；本轮没有跨平台构建动作。

## 13 落地范围（网页端与 Electron 端）

第 3 至 12 节的改动全部落在规划内核，即 simulator/backend/cyberarm/planner.py 与 server.py。算法只有这一份，网页端与 Electron 端都不重新实现：两边都由浏览器侧发起 HTTP 请求，服务端 make_plan 把任务交给 ProcessPoolExecutor(max_workers=2) 执行 plan_job。因此「把新方法应用到两个端」分成两件事——网页端确认没有旁路，Electron 端把冻结产物重建。

### 13.1 网页端

开发态（vite 代理把 /api、/models、/ws 转到 127.0.0.1:8765）直接调用 simulator/backend，改动一保存就生效，不需要任何构建步骤。

生产构建 simulator/frontend/dist 本轮没有重建，因为前端源码本轮没有改动：前端的职责只是把步长发过去并显示返回的时长与检查数，规划与碰撞检查完全在服务端。核对结果：

|---|---|
| simulator/frontend/dist/index.html | D28A6E8577EB688A7040888BAB5261109E2DE563869A047AE114677303740DE7 |
| simulator/frontend/dist/assets/index-yxgYvwQt.js | 94AABBE0A324D2DFF915459FE6EDE6CC8CE20124507E6085AB73B403A1A8F327 |

这三处的 dist 与 desktop/stage、desktop/dist/win-unpacked/resources/runtime 内的同一文件哈希一致，说明网页端与桌面端跑的是同一份前端。

### 13.2 Electron 端

桌面版的后端是 PyInstaller 冻结产物，算法已经被打包进 cyberarm-backend.exe，所以只改源码不会影响桌面上安装的版本，必须重新冻结。本轮重跑 PyInstaller（--onedir、--paths simulator/backend、入口 desktop/backend_entry.py）并同步产物：

| 位置 | 作用 |
|---|---|
| desktop/build/frozen/cyberarm-backend | 冻结输出 |
| desktop/stage/backend | prepare.cjs 复制到的中间目录 |
| desktop/dist/win-unpacked/resources/runtime/backend | 交付应用实际加载的后端 |

三处 cyberarm-backend.exe 的 SHA-256 均为 2856759D5FA59AF73BD02F5309FD08C3FD126F7E34B4F03E15484D432463FB77（14,864,926 字节），与改动前的旧版本不同即新算法已进包。三处目录共 219 个文件，逐文件路径与大小完全一致。

### 13.3 每个规划进程约 1 秒的冷启动

冻结后端里 ProcessPoolExecutor 在构造时就急切地起了两个 worker，而每个 worker 的第一次任务要付一次性成本。拆开度量后（simulator/.cache/probe_coldstart.py）：import cyberarm.planner 641 ms（单独 import scipy.optimize 要 653 至 677 ms，planner 原先在模块级导入它）、解压 collision.npz 373 至 429 ms、夹爪扫掠半径 8 至 10 ms —— 也就是说整份一次性成本的大头是一个只有冷种子才用得到的库。两项改动：

1. scipy.optimize 改为函数内惰性导入（planner.least_squares_solver()，首次真正调用时才加载并缓存）。导入 planner 从 641 ms 降到 127 ms。关节预览根本不进这条分支；可达的末端目标由阻尼高斯-牛顿 polish 直接答出，也不进；只有远离工作空间、需要跑完整套随机种子的目标才会加载它。
2. warm_worker() 在服务启动时向池里放两个预热任务（见 server.py 的 lifespan），并把惰性求解器的加载放到后台守护线程里，让它在窗口打开期间完成。预热失败只记一条事件日志，不影响服务。

惰性导入的有效性用两个探针确认（probe_solver_use.py）：冷种子路径确实加载了求解器并给出正确残差（近点 0.10/0.16/0.20 拒绝，残差 81.765 mm），而紧随其后的可达目标 0.9 ms 返回；冻结产物里同样正常（probe_shipped_lazy.py 的远目标返回「最佳位置误差 1189.698 mm」而非 ImportError）。

效果验证（simulator/.cache/probe_shipped_sidecar.py、probe_first_click.py，直接启动交付产物里的 cyberarm-backend.exe 并发 HTTP 请求）：

| 场景 | 实测 |
|---|---|
| 到 ready | 0.94 s（系统缓存热）至 6.33 s（PyInstaller 首次解包） |
| 预热完成后再预览，关节 8° | 49 至 82 ms / 25 个检查区间 |
| 关节 30° | 167 至 180 ms / 92 个检查区间 |
| 可达采样，无方向约束 | 49 至 89 ms / 3500 点 |
| 可达采样，约束方向 [1,0,0] | 43 ms / 25 点 |
| 窗口刚显示就点预览（预热尚未跑完） | 第一次 792 至 986 ms，第二次 49 至 75 ms |

最后一行说明剩余的一次性成本位置：它与启动预热并发，所以「启动后第一次点击」仍可能等约 0.8 至 1 秒，「之后每次」都在 50 ms 量级。按时间轴复测（probe_shipped_timeline.py）可见它在 ready 后约一秒内消失：0.7 s 点击 680 至 986 ms，0.8 s 点击 95 ms，此后 49 至 72 ms。同一时间轴上，加载前端首页 83 至 93 ms、33 MB 的 robot.glb 237 至 261 ms，所以用户看到窗口、模型落到场景里的这段时间已经把预热覆盖掉。另有一次并发发两个规划请求时，第二个返回 409，这是服务原有的「同一时刻只处理一个规划」保护，不是本轮改动引入的。

### 13.4 可达采样向量化

workspace_job 原先把每个样本分别送进正运动学，3500 次库调用加逐点叉乘占了大头。现在采样仍然保持 3500 次逐样本 rng.uniform 不变，因为一次性按 size=(3500,6) 抽取会改变默认随机流（对照结果为 np.array_equal False），逐样本循环才能保证点集与旧版完全相同；运动学改用已有的 tcp_frames(r, samples[:,:5]) 批量算，方向筛选改成一次矩阵乘法加比较，不再逐点循环。

对照结果（simulator/.cache/probe_ws_equiv.py、probe_ws_diff.py）：无方向约束与方向 [1,0,0] 的点数两版完全相同（3500 与 25），坐标最大差 1.11e-13 mm（浮点末位）；方向 [0,0,1] 与 [0,1,0] 两版都得 0 点。耗时 95.6 ms 降到 33.4 ms。

### 13.5 预览路径点的批量正运动学

plan_job 每确认一段还要为前端折线取 15 个采样点，原先在循环里逐个调用 r.fk()。工具中心只由五个串行关节决定，这里改用同一批 tcp_frames 一次算完（改动前后的路径数组经 API 对照：15 点、最大差 5.551e-14 mm）。
