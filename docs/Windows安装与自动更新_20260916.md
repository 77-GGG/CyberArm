# Windows 安装与自动更新

## 已实现行为

CyberArm Studio 使用 NSIS 安装程序和 `electron-updater`（首次发布的版本为 0.6.0，当前发布版本见 `desktop/package.json`）：

1. Windows 安装版启动约 10 秒后检查 `77-GGG/CyberArm` 的最新正式 GitHub Release。
2. 发现更高版本时显示版本号和发布说明，由用户决定是否下载。
3. 下载期间软件可以继续运行，Windows 任务栏显示下载进度。
4. 下载完成后可以立即重启安装、退出软件时安装或稍后处理。
5. 安装前复用桌面端关闭流程：停止当前运动、断开实机串口、终止本地后端，然后启动 NSIS 更新程序。
6. “帮助 → 检查更新”可以手动检查。开发模式和自动化测试不会访问更新服务器。

更新失败时保留当前安装版本。安装程序不会删除用户数据；卸载配置也保留应用数据。

> **仓库必须保持公开。** electron-updater 以匿名方式访问 GitHub Release
> (https://github.com/77-GGG/CyberArm/releases.atom)。仓库转为私有后，
> 该请求会返回 404，所有用户的检查更新都会失败（2026-09-17 已实际发生并复现）。
> 如果需要私有仓库，必须改用带令牌的更新服务器方案，而不是 electron-updater 的
> GitHub Provider 匿名模式。

## 本地构建

在 `desktop` 目录执行：

```powershell
npm ci
npm run build:win
```

构建过程会重新构建前端、C++ 核心和 PyInstaller 后端，并生成：

```text
desktop/dist/CyberArm-Studio-Setup-<版本>-x64.exe
desktop/dist/CyberArm-Studio-Setup-<版本>-x64.exe.blockmap
desktop/dist/latest.yml
desktop/dist/win-unpacked/CyberArm Studio.exe
```

其中安装器用于首次安装，`latest.yml` 和 `.blockmap` 是自动更新所需资产，三者发布时必须来自同一次构建。

## 发布新版本

1. 更新 `desktop/package.json` 和 `desktop/package-lock.json` 中的版本号。
2. 提交并推送通过测试的代码。
3. 创建与版本完全一致的标签，例如：

   ```powershell
   git tag v0.8.0
   git push origin v0.8.0
   ```

4. `.github/workflows/windows-release.yml` 会在 Windows runner 上重新构建并测试安装版。
5. 测试通过后，工作流把安装器、blockmap 和 `latest.yml` 上传到对应 GitHub Release。

工作流会拒绝标签和 `desktop/package.json` 版本不一致的发布。日常分支和普通提交不会创建 Release。

## 更新链路验收

完整升级验收需要两个真实版本：

1. 安装旧版本，例如 0.7.0。
2. 发布更高版本，例如 0.8.0。
3. 打开旧版本，确认能发现、下载并安装 0.8.0。
4. 在运动中请求安装，确认应用先安全停止运动并断开串口。
5. 更新后确认项目文件、日志和用户设置仍存在。

已核对的发布链路：标签推送由 `.github/workflows/windows-release.yml` 在干净 Windows runner 上重建并冒烟测试安装版，再上传三个资产；本地核对确认 Release 中安装包的 SHA-512 与 `latest.yml` 声明值一致，更新源的最新正式 Release 为 `v0.7.0`。上述第 3 步的交互式升级仍需要在装有旧版本的机器上手工确认。

当前安装包未配置受信任的 Windows 代码签名，Windows SmartScreen 可能显示“未知发布者”。自动更新元数据和下载校验已由 electron-builder/electron-updater 管理，但公开分发前仍应配置长期稳定的代码签名证书。
